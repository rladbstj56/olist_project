# Olist 후속 정비 작업 해설서

최종 갱신: 2026-10-04. 이 문서는 이번 대화에서 무엇을 왜 바꿨는지 사용자가 이해하고 설명하기 위한 안내서입니다. 자세한 코드 근거와 과거 상태는 [모델링 결정 로그](modeling_decision_log.md), 시간 검증의 조건과 결과는 [시간 분할 설계서](temporal-validation-plan.md)를 함께 봅니다. 이 문서의 최신 상태와 과거 로그의 ‘미완료’ 표현이 다르면 기록 날짜를 구분합니다.

## 우리가 해결하려는 문제

이 프로젝트는 배송이 지연된 주문에서 리뷰 점수가 어떻게 달라지는지 살펴보고, 낮은 리뷰 점수를 받을 가능성이 높은 주문을 미리 확인하는 데 목적이 있습니다. 배송이 끝난 뒤 사용하는 Track A와 주문 시점의 정보를 쓰는 Track B를 구분했습니다. Track C는 배송 속도를 바꾸는 모델이 아니라, 예상 배송일을 얼마나 보수적으로 제시할지 검토하는 모델입니다.

후속 정비는 모델을 무조건 더 좋게 만드는 작업으로 시작하지 않았습니다. 포트폴리오에 쓴 설명이 실제 코드와 맞는지, 보고한 성능이 어떤 조건에서 나온 숫자인지 확인하는 작업이었습니다. 확인 과정에서 전체 데이터로 결측치를 채운 점과 아이템 행 기준 평가라는 한계를 발견했고, 이를 단계별로 검증하고 수정했습니다.

## 1. 주문과 아이템은 무엇이 다른가

한 주문에 컵2개와 접시1개가 들어 있으면 주문은1건이지만 아이템 행은 여러 개입니다. 각 행에는 상품 가격·무게·판매자 등의 정보가 있고 주문 리뷰가 함께 붙습니다. 따라서 한 주문의 리뷰가 여러 행에서 반복될 수 있습니다.

| 숫자 | 정확한 의미 |
|---|---|
| 109,294행 | 전처리 완료 데이터의 전체 주문·아이템 행 |
| 95,784주문 | 위 데이터에서 주문 ID를 한 번씩 센 수 |
| 87,482행 | EDA 학습·검증 영역에 들어간 아이템 행 |
| 76,627주문 | 그 EDA 영역의 고유 주문 수 |
| 100,107행·87,872주문 | 주 분류 모델에서 리뷰3점9,187행을 제외한 분할 전 표본 |
| 19,985행·17,575주문 | 주 분류 모델의 테스트 표본 |

87,482행은 중복 제거 후 숫자가 아니라 테스트 주문을 따로 떼어낸 뒤 남은 EDA 영역입니다. 리뷰 통계에서76,627주문으로 줄인 것은 같은 주문 리뷰를 상품 수만큼 반복 세지 않기 위해서입니다. 그때 쓰는 리뷰·배송 변수는 주문 내 값이 같다는 것도 확인했습니다.

**모델 학습에서 임의로 상품 하나만 남긴 것은 아닙니다.** 상품 정보는 아이템별로 유지했습니다. 앞으로 주문당1행으로 학습하는 새 모델을 만든다면 상품 수·총가격·최대거리처럼 여러 상품의 정보를 합치는 규칙부터 설계해야 합니다.

## 2. 통계와 차트에서 바로잡은 말

지연 구간은 실제 시각 차이를 일수로 계산하고 소수 첫째 자리로 반올림한 값으로 구분합니다. 따라서 `1–3일` 같은 표시보다 `0일 초과·3일 이하`가 정확합니다. 기존 모델 입력 문자열은 유지하고 사람이 읽는 표시만 고쳤습니다.

지연 주문 중 짧은 구간2,086주문과 3일 초과 구간3,983주문을 비교하면 리뷰 평균이 약1.83점 다릅니다. 이것은 **관찰한 두 집단의 평균 차이**입니다. Mann–Whitney U 검정은 리뷰 점수 분포를 비교하며, 순위 기반 효과크기0.594는 차이의 크기를 별도로 설명합니다. 저장된 p값0.0은 계산 표현 한계여서 보고에서는 `p<0.001`로 씁니다.

이 결과가 ‘배송을3일 늦추면 리뷰가1.83점 내려간다’는 뜻은 아닙니다. 상품 문제·지역·판매자 등의 다른 요인이 함께 작용할 수 있습니다. 또한 ‘3일이 최적 기준’이라는 증명도 아닙니다. 이 프로젝트에서는 **우선 모니터링할 구간 후보**로 설명합니다.

## 3. 리뷰3점을 왜 제외했는가

별점1·2점은 낮은 만족도,4·5점은 긍정으로 보고, 중간인3점은 주 모델에서 제외했습니다. 비교적 구분이 명확한 두 집단을 분석하기 위한 정책 선택입니다. 모든3점 고객이 실제로 중립이라고 증명한 것은 아닙니다.

3점을 포함하는 다른 정책의 재현율0.597도 민감도 결과로 보존했습니다. 정책을 바꾸면 ‘위험 고객’의 정의와 평가 대상이 함께 달라지므로 재현율 숫자만 비교해 어느 정책이 우월하다고 말하면 안 됩니다.

## 4. 학습·검증·테스트는 각각 무엇인가

- 학습 데이터: 모델이 패턴과 결측 대체 기준을 배우는 자료입니다.
- 검증 데이터: 어떤 점수부터 위험으로 표시할지 등 선택 기준을 정하는 자료입니다.
- 테스트 데이터: 정해진 모델과 기준을 평가하는 자료입니다.

같은 주문의 아이템이 학습과 테스트에 나뉘면, 모델이 사실상 같은 주문을 이미 본 상태에서 평가될 수 있습니다. 기존 코드는 주문 ID로 묶어 분리했고, 주문 교집합0을 확인했습니다. 다만 주문별로 나눴다는 것과 주문별로 한 번씩 성능을 계산한다는 것은 서로 다릅니다.

기존 A/B 분할은 학습64,103행, 검증16,019행, 테스트19,985행입니다. UI는 별도 경로로80,122행을 학습하므로 A/B의 성능을 UI 성능이라고 그대로 설명하지 않습니다.

## 5. 결측치 처리에서 무엇이 문제였는가

예를 들어 상품 무게가 비어 있을 때 전체 데이터의 가운데 값으로 채우면, 아직 평가에만 써야 할 주문의 무게까지 대체 기준 계산에 들어갑니다. 리뷰 정답을 직접 훔쳐본 것은 아니지만 평가 영역의 정보를 학습 준비 과정에 사용한 셈입니다.

기존 코드는 도시별 좌표 최빈값과 상품·거리 중앙값을 전체 데이터에서 계산했습니다. 이 사실만으로 성능이 크게 부풀려졌다고 단정하지 않고, 같은 분할·모델 설정에서 수정 전후를 비교했습니다.

수정 후에는 학습 자료로 대체 기준을 계산하고 검증·테스트에는 그 값을 적용만 합니다. 학습에 없던 도시의 좌표를 임의로 만들지 않으며, 거리 계산이 끝내 불가능하면 학습 거리 중앙값을 사용합니다. 교차검증에서도 작은 학습 묶음마다 기준을 다시 계산합니다.

이 과정을 Pipeline에 넣은 이유는 실행할 때마다 누군가 처리 순서를 기억해야 하는 상태를 피하기 위해서입니다. 모델을 학습하면 그 학습 자료로 대체 기준도 함께 정해지고, 예측할 때는 저장된 기준을 재사용합니다.

## 6. 수정했더니 성능이 좋아졌는가

이번 수정의 목적은 성능 숫자를 올리는 것이 아니라 평가 조건을 바로잡는 것이었습니다.

| A/B 테스트 지표 | A 수정 전 → 후 | B 수정 전 → 후 |
|---|---|---|
| 위험 정밀도 | 0.286932 → 0.284381 | 0.234589 → 0.234436 |
| 위험 재현율 | 0.678069 → 0.672315 | 0.619246 → 0.616368 |
| AP | 0.505432 → 0.504897 | 0.289262 → 0.289564 |

모든 지표가 좋아진 것은 아닙니다. 테스트를 이미 확인한 뒤의 비교이므로 완전히 새로운 데이터에서 성능을 보장한 실험도 아닙니다. 기존 전처리 문제의 영향을 같은 조건에서 비교한 결과입니다. 새 코드를 실제 학습했을 때 앞선 실험의 검증·테스트 확률과 정확히 일치하는 것도 확인했습니다.

정밀도는 ‘위험하다고 고른 것 중 실제 위험 비율’, 재현율은 ‘실제 위험한 것 중 찾아낸 비율’입니다. AP는 여러 기준점에서 위험 사례를 얼마나 앞쪽에 배치했는지 평가하는 요약 점수이며 실제 위험 확률과 다릅니다.

## 7. UI와 Track C에서는 무엇을 바꿨는가

UI는 사용자가 보는 Streamlit 화면입니다. 가격·거리·상품 정보를 넣으면 위험도와 배송일 검토값을 보여줍니다. 학습 코드를 고쳤어도 이 화면이 예전 전처리로 학습하면 다른 모델을 쓰게 되므로 UI B/C도 수정했습니다.

사용자가 거리를 직접 입력한 경우에는 그 거리를 존중하고 구간만 자동 계산합니다. 원본 좌표를 받는 배치 예측과 수동 입력을 구분했습니다. 예시에는 주문 ID와 아이템 번호를 같이 표시하며, 고위험 목록은 주문별로 가장 위험도가 높은 아이템을 대표로 보여줍니다. 학습 자료에서 나머지 아이템을 지우는 방식이 아닙니다.

Track C의90% 분위수 예측은 배송 소요일 분포의 높은 쪽 값을 검토값으로 사용하는 접근입니다. ‘90% 주문에서 반드시 지켜지는 약속’이라는 인증은 아닙니다. 실제 도착일을 고정하고 예상 배송일을 늘리면 ‘약속보다3일 넘게 늦었다’는 비율이 줄 수 있지만, 택배가 빨라진 것은 아닙니다.

수정 전후10회 학습 결과 UI B의 위험 분류는 같았고 확률은 일부 달라졌습니다. Track C 결과는 지표별로 조금씩 달라졌습니다. 자동 테스트8개와 실제 Chrome 기본 화면·거리 입력을 확인했습니다. 작은 창에서는 긴 카드 라벨이 말줄임되고 표는 가로 스크롤이 필요합니다. 모든 화면 크기나 분위수 선택의 재학습까지 확인한 것은 아닙니다.

## 8. 주문 단위로 다시 평가한 이유와 결과

CS 담당자는 보통 상품 행마다 같은 주문을 반복 확인하지 않습니다. 기존 성능이 실제 주문 확인 업무와 얼마나 대응하는지 보려면 주문을 한 번씩 세는 평가가 필요합니다.

기존 모델의 예측을 그대로 두고 주문 안에서 가장 높은 위험 점수를 대표로 사용했습니다. 이는 한 상품이라도 위험하면 주문을 확인하는 현재 UI 방식과 같습니다. 평균 점수를 쓰는 경우도 보조 비교했지만 테스트에서 더 좋아 보인다는 이유로 규칙을 골라 바꾸지 않았습니다.

| Track B 기준 | 정밀도 | 재현율 | 확인 대상 |
|---|---:|---:|---:|
| 아이템 행 | 23.44% | 61.64% | 8,224행 |
| 주문 최대 점수 | 20.53% | 59.12% | 6,852주문 |

주문 기준으로 보면 위험 주문2,380개 중1,407개를 찾았습니다. 확인 대상으로 고른6,852개 주문 중1,407개가 실제 위험 주문입니다. 상품 정보를 삭제해서 성능이 떨어진 것이 아니라, 분모·가중치·점수 집계가 달라진 결과입니다. 최대 점수는 보정된 주문 불만 확률이라고 부르지 않습니다.

## 9. 이제 시간 분할은 왜 하는가

기존에는 과거와 이후 주문이 섞인 상태에서 주문 ID를 무작위로 나눴습니다. 실제 사용 상황은 과거 기록으로 배운 뒤 앞으로 들어오는 주문을 판단하는 흐름입니다. 시간에 따라 판매자·지역·상품 구성이나 지연 상황이 바뀌면 무작위 분할에서 본 성능과 다를 수 있습니다.

시간 분할은 이 차이를 확인하는 검증입니다. 예를 들어2017년12월 주문이라도 리뷰가2018년1월에 도착했다면,2018년1월1일에 학습하는 모델은 아직 그 리뷰를 정답으로 쓸 수 없습니다. 그래서 주문 날짜와 정답을 알 수 있는 날짜를 함께 확인합니다.

설계 점검에서는 학습 후보39,634주문 중2,780주문이 학습 마감일까지 배송·선택 리뷰 기록을 모두 확보하지 못했습니다. 이 자료를 빼는 것은 상품 정보 삭제와 다른 문제입니다. 당시 사용할 수 없는 미래 정답을 학습에 넣지 않기 위한 조건입니다. 자세한 기간·숫자·예외는 [시간 분할 설계서](temporal-validation-plan.md)에 있습니다.


### 시간 검증을 실제로 해보니

과거42,057개 아이템 행으로 한 번 학습한 뒤, 이후27,191개 행에 해당하는23,783주문을 평가했습니다. 주문별 최대 위험 점수를 쓰면 낮은 리뷰 주문2,715개 중1,744개를 찾습니다. 이것이 재현율64.24%입니다. 하지만 확인 대상으로 표시한12,639개 중 실제 낮은 리뷰는1,744개뿐이어서 정밀도는13.80%입니다. ‘많이 찾는다’와 ‘골라낸 대상이 정확하다’를 함께 봐야 하는 이유입니다.

특히 아이템이2개 이상인 주문은98% 이상이 표시됐습니다. 평균 점수로 묶어도 표시 비율이 높았습니다. 상품이 많아서 불만이 생긴다는 증거가 아니라, 이 모델과 기준이 복수 아이템 주문을 충분히 좁혀 주지 못한다는 진단입니다. 입력에 아이템 순번도 포함돼 있으므로 다음은 순번·상품 구성과 점수의 관계를 살펴볼 수 있습니다. 원인 확인 전 피처를 삭제하거나 기준을 바꾸지는 않았습니다.

검증 마감 때 정답이 없어 보류된 주문의 최종 낮은 리뷰 비율은36.08%, 실제 검증에 쓴 주문은15.53%였습니다. 미래 정답을 쓰지 않으려 제외한 결과, 빠르게 정답이 나온 주문 위주로 기준을 정했다는 한계가 생겼습니다. ‘시간 순서로 나눴으니 검증이 완벽하다’고 말하지 않는 이유입니다. [상세 결과와 근거](modeling_decision_log.md#30-시간-분할-track-b-1회-학습과-상품-수별-진단--2026-10-03)를 함께 확인합니다.

### 캡처와 포트폴리오는 어디까지 반영됐는가

화면 캡처는 Streamlit이 실제로 작동하고 한글·표·입력이 보이는지 확인한 기록입니다. 포트폴리오 이미지를 교체하려는 목적이 아니었습니다. 범용19쪽 포트폴리오는 이전 표현 교정까지 완료됐으며 이후 결측 처리 개선·주문 평가·이번 시간 평가 결과는 아직 넣지 않았습니다. NICE 제출본은 보존합니다. 다음 개정에서는 성능 향상 주장보다 어떤 문제를 발견하고 어떻게 검증했는지를 담는 안을 먼저 정리해야 합니다.

## 10. 어디까지 말할 수 있고 무엇은 남아 있는가

| 설명할 수 있는 사실 | 아직 주장할 수 없는 내용 |
|---|---|
| 분할·평가 단위·결측 대체 경로를 추적하고 수정함 | 모든 형태의 정보 누수가 해결됨 |
| 같은 조건의 수정 전후 결과와 예측을 저장함 | 실운영 성능이나 새 일반화 성능이 입증됨 |
| 주문별 위험 점수로 평가를 다시 계산함 | 주문별 피처로 새로운 모델을 학습함 |
| 관찰 데이터에서 지연·리뷰 연관성을 확인함 | 배송 지연의 인과 효과 또는3일의 최적성 입증 |
| 예상 배송일 검토값의 시뮬레이션을 수행함 | 실제 배송·만족도·매출이 개선됨 |
| 정한 시간 조건에서 Track B를1회 학습·평가함 | 모든 과거 피처를 완전히 복원하거나 실운영 효과를 입증함 |

과거 시점의 상품 카탈로그·좌표·예상 배송일 값이 지금 저장된 값과 같았는지, 취소·미배송 주문에서도 적용 가능한지, 최종 리뷰 선택이 어떤 영향을 주는지는 남은 한계입니다. 더 많은 실험을 했다는 이유만으로 이 한계가 자동으로 사라지지는 않습니다.

## 추가 진단: 상품이 같아도 순번 때문에 점수가 달라질 수 있었습니다

이번 모델은 아이템 순번도 입력으로 사용합니다. 같은 주문의 첫째·둘째에서 나머지21개 입력이 모두 같은1,666주문을 찾아 비교했습니다. 둘째 아이템의 위험 점수가 평균0.1395 더 높았고 위험 표시 수는 첫째915개, 둘째1,630개였습니다. 가격·무게·거리 등이 같은 경우에도 순번이 달라지면 모델 점수가 달라졌다는 뜻입니다. 실제 불만 확률이 그만큼 높아진다는 뜻은 아닙니다.

이런 패턴을 배울 수 있는 배경도 있습니다. 첫째 아이템은 모든 주문에 있지만 둘째 아이템은 복수 아이템 주문에만 있고, 학습 자료에서 이 집단은 낮은 리뷰 비율이 높았습니다. 또한 상품이 많은 주문은 같은 리뷰가 여러 학습 행에 반복됩니다. 단순히 중복 오류라고 볼 것은 아니지만 주문별 반영 비중은 달라집니다.

따라서 다음 후보는 상품을 하나만 남기는 것이 아니라 **모든 상품을 유지하면서 순번이라는 입력 하나만 빼고 비교하는 실험**입니다. 현재 모델의 순번 의존성을 확인한 것과 순번을 빼면 더 좋아진다는 결론은 다릅니다. 이 진단 당시에는 재학습 전이었으며, 후속 실행 결과는 아래 ‘순번을 실제로 빼 보니’에 기록했습니다. 상세 근거·재현표·후속 범위는 [결정 로그31절](modeling_decision_log.md#31-복수-아이템-과다-선별의-순번구성-진단--2026-10-03)에 남겼습니다.


## 순번을 실제로 빼 보니 — 2026-10-04

모든 상품 행은 그대로 두고 모델 입력에서 순번만 뺀21개 피처 모델을 한 번 학습했습니다. 순번이 달라도 점수가 변하지 않는 것은 확인했지만, 검증 자료의 주문 기준 AP는0.244에서0.200으로 낮아졌습니다. 테스트에서도 정밀도13.80%→12.97%, AP0.172→0.142로 낮아지고 확인 대상은12,639주문에서13,711주문으로 늘었습니다. 따라서 새 모델을 기본 모델로 바로 바꾸지는 않았습니다.

복수 아이템 주문의 과도한 표시는 줄었습니다. 아이템2개 주문은98.33%에서67.99%로 내려갔습니다. 대신 단일 아이템 주문의 표시 비율이48.14%에서56.30%로 늘었습니다. 한 문제를 줄였어도 전체가 좋아졌는지는 따로 봐야 한다는 사례입니다.

순번은 불필요하다고 확인된 열이 아니라, 주문 구성과 연결된 신호를 갖는 열이었습니다. 다른 입력에도 상수나 완전히 같은 열은 없었습니다. 가격 합계·비율과 SP 경로 변수는 다른 열로 계산할 수 있지만, 트리 모델이 유용하게 쓸 수도 있으므로 계산상 중복과 예측상 불필요를 구분합니다. 다음은 후보 묶음을 하나씩 비교하는 설계이며 무조건 여러 열을 삭제하지 않습니다. 근거와 전체 표는 [결정 로그32절](modeling_decision_log.md#32-순번-제외-21개-피처-비교와-제거-후보-점검--2026-10-04)에 있습니다.
