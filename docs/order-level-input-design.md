# 주문 전체를 직접 예측하는 입력 설계

작성일: 2026-10-05. 갱신일: 2026-10-10. 상태: **O39 입력 구현·검증 완료, 분류 모델 학습 전**.

사용자가 주문당 한 행, 아이템 순번 미사용, 모든 상품을 활용한 주문 전체 예측 방향을 승인했습니다. 이 문서는 집계와 검증의 계약입니다. 과거 모델·데이터·UI·포트폴리오·NICE는 이번 설계로 변경하지 않습니다. 상세 경과는 [결정 로그35절](modeling_decision_log.md#35-주문-전체-입력-설계--2026-10-05)을 확인합니다.

## 1. 목적·단위·예측 시점

- 입력 단위: 주문 한 개에 속한 모든 아이템의 구매 확정 시점 정보입니다. 한 주문에서 첫 아이템만 남기지 않습니다.
- 학습·정답·예측·평가 단위: 모두 주문 한 개입니다. 리뷰1·2점은 위험0,4·5점은 긍정1,3점 제외 정책은 유지합니다.
- 출력: 주문의 낮은 리뷰 위험 점수 한 개입니다. 아이템별 예측을 먼저 만든 후 최댓값을 취하지 않습니다. 상품별 불만 원인이나 보정된 실제 발생 확률이라고 설명하지 않습니다.
- `order_id`는 주문 연결·분할 키, `order_item_id`는 원본 아이템 연결·중복 검사 키로만 보존합니다. 둘 다 모델 입력에서 제외하며 순번을 이용해 대표 상품·최빈값 동률을 선택하지 않습니다. product/seller ID도 개수 계산에만 쓰고 ID 문자열을 입력하지 않습니다.
- 주문 시점이란 가격·상품·판매자·주소·배송 약속이 확정된 시점이라는 설계 가정입니다. 당시 카탈로그·예정일·좌표의 변경 이력은 확보되지 않았습니다. 실제 배송일·지연일·리뷰는 입력에서 배제합니다.

## 2. 고정 표본과 원본 점검

기존 시간 배정표 `outputs/experiments/temporal-validation-20261003-202427/assignments.csv`의 eligible 주문을 그대로 사용합니다. 학습36,854주문/42,057아이템, 검증14,621주문/16,679아이템, 테스트23,783주문/27,191아이템입니다. 총75,258주문/85,927아이템입니다. 기간·배송/리뷰 기록 확보 조건·이상 시각 제외는 [시간 설계서](temporal-validation-plan.md)를 유지합니다.

2026-10-05 읽기 전용 점검에서 다음을 확인했습니다.

| 검사 | 결과 |
|---|---:|
| 위 주문의 원본 `olist_order_items_dataset.csv`와 아이템 키 차이 | 0행 |
| 주문 내 review_score·구매 시각·예정 도착일·고객 주 불일치 | 각0주문 |
| 위 공통 변수 결측 | 각0행 |
| product_id·seller_id 결측 | 각0행 |
| 가격0 이하·음수 배송비 | 각0행 |

이번 표본은 해당 주문의 모든 원본 아이템을 포함합니다. 전체 원본 주문 모집단을 포함한다는 의미는 아닙니다. 배송 완료·최종 리뷰·3점 제외 및 기록 확보 조건으로 선택된 후향적 표본이라는 한계는 유지합니다. 원본 상품을 더 추가하거나 표본을 조용히 바꾸지 않습니다. 구현 시 이 검사를 다시 실행하고 어긋나면 원인을 기록합니다.

## 3. 입력 사전: 순번과 무관한 집계

최초 설계는 아래39개 입력에 명시적 아이템 수1개를 추가하는 비교입니다. 카테고리 차원 수는 학습 자료에서만 확정하며 현재 대분류6개를 확인했습니다. 원본 열명은 유지하고 새 주문 입력명은 별도 모델 계약으로 관리합니다.

| 묶음 | 제안 입력명·집계 | 수 | 이유와 정보 손실 |
|---|---|---:|---|
| 공통 주문 조건 | `purchase_dayofweek`, `purchase_month`, `expected_delivery_days`, `is_sp_customer` | 4 | 주문 내 값이 같음을 검사한 뒤 하나의 값 사용. 대표 아이템 선택이 아닙니다. |
| 상품·판매자 다양성 | `distinct_product_count`, `distinct_seller_count` | 2 | ID 고유값 수. 종류와 판매자 구성은 남기고 ID 자체는 사용하지 않습니다. |
| 상품 가격 | `price_sum`, `price_mean`, `price_max`, `price_std` | 4 | 총규모·평균·큰 상품·가격 편차. 상품별 조합과 가격/무게의 결합 관계는 손실됩니다. |
| 배송비 | `freight_sum`, `freight_mean`, `freight_max` | 3 | 원본 아이템별 부과액 합계·평균·최대. 기존 행별 값을 한 번씩 합산합니다. |
| 배송비 부담 | `freight_to_price_ratio` = 배송비 합/가격 합 | 1 | 개별 행 비율의 평균과 구분합니다. 가격 합0이면 결측으로 두고 학습 주문 기준 처리합니다. |
| 상품 무게·세 변 길이 | `weight_mean/max`, `length_mean/max`, `height_mean/max`, `width_mean/max` | 8 | 각 아이템 특성의 평균·최대. 상자 합산 크기나 실제 포장 무게로 해석하지 않습니다. |
| 거리 | `distance_mean`, `distance_max`, `distance_std` | 3 | 고객–판매자 거리의 아이템 기준 평균·최대·편차. 배송 순서·실제 주행거리가 아닙니다. |
| 지역 구성 | `cross_state_share`, `seller_sp_share` | 2 | 주간 배송·SP 판매자 아이템의 비율. 같은 판매자의 여러 아이템도 각각 포함됩니다. |
| 상품 대분류 구성 | 학습 대분류별 `category_share_*`6개 + `category_share_unknown` | 7 | 최빈 카테고리 하나를 고르지 않고 아이템 비율로 복수 구성을 보존합니다. 소분류 정보는 첫 설계에서 생략합니다. |
| 원본 결측 비율 | `missing_weight/length/height/width_share`, `missing_distance_share` | 5 | 대체 전 결측 아이템 비율. 거리 결측은 계산에 필요한 원본 좌표 중 하나라도 없는 경우입니다. 결측 패턴도 수와 간접 연관될 수 있습니다. |
| 명시적 상품 수·비교용 | `item_count` | +1 | 고유 상품 종류 수가 아니라 원본 아이템 행 수입니다. 순번의 최대값으로 계산하지 않습니다. |

첫 번째 비교는 **O39: 위39개, O40: 같은39개+item_count**로 고정합니다. 단, O39에도 합계/평균·고유상품 수 등이 있어 상품 수를 유추할 수 있습니다. 특히 가격 합/평균으로 아이템 수가 드러납니다. 따라서 ‘상품 수 영향을 완전히 제거한 모델’이 아니라 **명시적 item_count를 추가하는 효과**만 비교합니다. 상품 수 정보 자체를 배제하려면 합계·종류 수·결측 비율 등 대리정보까지 별도 재설계해야 하며 이번 두 조건의 결과로 그 효과를 주장하지 않습니다.

파생값은 실제 위험의 인과 원인이어야만 하는 것은 아니지만, 사용 목적·계산·시점이 설명 가능해야 합니다. 상관이 작다는 이유나 총점이 조금 높다는 이유만으로 임의 추가/삭제하지 않습니다. 이 집계안은 모든 상품 행을 사용하되 모든 원본 정보를 손실 없이 보존하는 방식은 아닙니다.

## 4. 결측·범주·집계 순서

1. 원본 키·주문 공통값·정답 일치·아이템 완전성을 검사하고 기존 주문 배정으로 분리합니다. 주문 리뷰를 임의의 첫 행이나 다수결로 결정하지 않습니다.
2. 학습 주문에 속한 아이템에서만 기존 도시 좌표 최빈값·상품/거리 중앙값을 학습합니다. 첫 비교에서는 기존 item-level 대체 방식을 유지하며 그 통계가 아이템 가중임을 기록합니다. 검증·테스트에서 재계산하지 않습니다.
3. 대체 전 결측 표시를 보존한 뒤 학습 통계로 아이템 값을 변환합니다. 결측 아이템을 집계에서 빠뜨리거나 모두 결측인 합계를0으로 처리하지 않습니다.
4. 교정된 모든 아이템을 위 사전대로 집계합니다. 평균은 아이템 행 기준, 표준편차는 모집단 정의 `ddof=0`, 아이템1개면 표준편차0입니다. 합계/평균 계산은 값 기준 정렬 등 순번에 독립적인 결정적 집계로 구현해 부동소수 덧셈 순서 영향을 통제합니다.
5. 카테고리 사전은 학습 아이템에서만 만듭니다. 비율의 분모는 해당 주문 전체 아이템 수이며 비율 합은1입니다. 결측/검증·테스트 신규 범주는 unknown에 포함합니다. 범주 동률에 따른 첫 상품 선택은 없습니다.
6. 남은 주문 집계 결측의 대체는 학습 주문 기준으로만 fit합니다. 전체 결측 열·정의되지 않은 공통값은0으로 조용히 채우지 않고 학습 전에 원인과 처리 방침을 확인합니다.
7. 날짜·리뷰·키·순번·제품/판매자 ID가 최종 입력에 섞이지 않았는지 검사합니다. 같은 변환기를 검증·테스트와 나중 UI에서 재사용합니다.

## 5. 구현할 함수의 역할

다음 표는 최초 인터페이스 설계입니다. 실제 구현 함수와 완료 범위는 아래10절 및 결정 로그36절에 기록했습니다.

| 구성 | 입력 → 출력 | 필요 이유·판단 규칙 |
|---|---|---|
| 주문 입력 변환기 `fit` | 학습 아이템·원본 → 저장 대체 통계·학습 범주 사전 | holdout 정보 없이 변환 기준을 확정합니다. 정답을 집계 피처 계산에 사용하지 않습니다. |
| 주문 입력 변환기 `transform` | 아이템 전체·저장 기준 → order_id별 피처 표 | 모든 상품을 사용하고 순번을 제외합니다. 주문 공통값 불일치는 오류로 보고합니다. |
| 주문 라벨 생성 | 주문/아이템 키·리뷰 → order_id별 라벨 | 주문 내 라벨 일치 확인 후 유일한 라벨만 연결합니다. |
| 실험 실행 진입점 | 고정 배정·O39/O40 정의 → 학습 모델·검증/테스트 예측·비교표 | 같은 자료로 계획된 조건만 실행하고 산출물을 분리합니다. |

## 6. 학습·평가 조건과 채택 판단

- 구현 승인 후 계획된 학습은 O39·O40 각각1회, 총2회입니다. 이 설계 단계에는 학습0회입니다. LightGBM 기존 하이퍼파라미터를 출발점으로 고정하고 탐색·추가 튜닝·train+valid 재학습은 포함하지 않습니다.
- 주문당1행이므로 `1/item_count` sample weight는 추가하지 않습니다. `class_weight='balanced'`는 **학습 주문 라벨 수**로 계산합니다. 기존 아이템 모델과 클래스 배수도 달라지므로 전체 차이를 순번 제거 하나의 효과로 해석하지 않습니다. O39/O40 간 조건은 동일합니다.
- 모델은 주문 점수를 직접 출력합니다. 기존 후보의 주문 최대 집계 점수와 같은 주문 키·정답으로 비교하며, 기존 아이템 행 AP를 새 주문 AP와 섞지 않습니다.
- 1차 비교는 검증 주문 AP와 동일 확인량5·10·20·30·40·50%의 정밀도·재현율·탐지 수입니다. 정답과 무관한 ID 동점 규칙과 동점 범위를 유지합니다. 월별·아이템1/2/3개 이상, 단일/복수 판매자 결과도 보고합니다.
- 고정 기준 비교용으로 기존 임계값 선택 함수의 규칙을 검증 **주문**에 적용합니다. 기존 아이템 검증 기준과 선택 단위가 달라졌음을 표시합니다. 최종 UI 운영 기준은 처리량·놓침 비용 합의 전 확정하지 않습니다.
- 입력 불변성·누수·키 정합성은 통과해야 하는 조건입니다. 성능이 좋아도 실패하면 채택하지 않습니다. 집계 입력의 설명과 정보 손실도 함께 검토합니다.
- 검증 결과로 후보를 정리한 뒤 테스트는 조건을 바꾸지 않고 보고합니다. 기존 검증·테스트는 이미 반복 열람했으므로 독립적인 최종 검증으로 부르지 않습니다. 검증 우위를 실운영 개선으로 주장하지 않고, 실운영 신뢰에는 추가 기간/새 데이터 또는 별도 확정 평가가 필요합니다.
- 한 지표 최대값만으로 자동 채택하지 않습니다. 동일 확인량의 탐지, 월별/집단별 악화, 순서 불변성, UI 적용 가능한 입력을 함께 보고 채택 근거를 제시합니다. 개선이 없으면 보류하고 기존 후보를 비교 기준으로 보존합니다.

## 7. 필수 검사와 산출물

- 주문당1행·주문 교집합0·동일 시간 배정·라벨 일치·원본 상품 수 보존을 확인합니다.
- 아이템 행을 섞기, 순번 재부여, 상품/판매자 ID 문자열을 일대일 재명명하기에 대해 집계 입력과 예측이 같아야 합니다. ID 고유값 수를 바꾸는 재명명은 해당하지 않습니다. 수치 허용오차와 경계 분류까지 보고합니다.
- 주문1개/아이템1개, 같은 상품 반복, 여러 상품·판매자, 결측·신규 범주·동일 최댓값 사례를 고정 예시로 검사합니다. 다른 주문 추가·순서 변경이 기존 주문의 transform 결과를 바꾸지 않아야 합니다.
- 검증/테스트 값 변경이 학습 대체값·범주 사전을 바꾸지 않는지, fit이 학습 영역에만 수행되는지 확인합니다.
