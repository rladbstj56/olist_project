# Olist CS 리스크 분석 및 낮은 만족도 리뷰 조기 탐지

처음 읽는 분을 위한 [전체 작업 해설서](docs/olist-project-walkthrough.md)와 [시간 분할 검증 설계·실행](docs/temporal-validation-plan.md)를 제공합니다. 2026-10-03 별도 시간 검증은 주문 최대 점수 기준 정밀도13.80%·재현율64.24%이며 확인 대상 비율53.14%와 복수 아이템 주문 선별 한계를 확인했습니다. [상세 결과](docs/modeling_decision_log.md#30-시간-분할-track-b-1회-학습과-상품-수별-진단--2026-10-03)는 아래 과거 무작위 분할 성능과 평가 조건이 다르며 기존 UI에 적용하지 않았습니다.

Brazilian Olist e-commerce 공개 데이터를 기반으로, 배송 지연과 고객 리뷰의 관계를 분석하고 낮은 만족도 리뷰 가능성을 사전에 탐지하는 운영 분석 프로젝트입니다.

이 프로젝트는 단순히 리뷰 점수를 예측하는 것이 아니라, **배송 완료 후 원인을 진단하는 모델**과 **주문 시점에 위험 주문을 선별하는 모델**을 분리해 설계한 것이 핵심입니다. 팀 프로젝트 이후 개인 고도화 과정에서 데이터 단위, 정보 누수 가능성, 사전 예측 가능성을 다시 점검했습니다.

## 1. 프로젝트 개요

| 항목 | 내용 |
| --- | --- |
| 주제 | 배송 지연과 고객 리뷰 하락 간 관계 분석, 낮은 만족도 리뷰 위험 탐지 |
| 데이터 | Olist 주문, 고객, 상품, 판매자, 리뷰, 위치 데이터 |

## 2. 문제 정의

Olist 데이터에서는 배송이 늦어질수록 리뷰 점수가 낮아지는 패턴이 관찰됩니다. 하지만 실무 관점에서는 단순히 “배송이 늦으면 리뷰가 나빠진다”에서 멈추면 부족합니다.

이 프로젝트에서는 다음 질문으로 문제를 구체화했습니다.

1. 배송 지연은 리뷰 점수 하락과 통계적으로 유의하게 연결되는가?
2. 며칠 이상 지연될 때 CS 리스크가 커지는 운영 기준으로 볼 수 있는가?
3. 배송 완료 후에만 알 수 있는 정보와 주문 시점에 이미 알 수 있는 정보를 구분하지 않으면 모델 평가가 왜곡되지 않는가?
4. 리뷰가 작성되기 전에 위험 주문을 먼저 선별할 수 있는가?

## 3. 데이터와 인스턴스 기준

최종 분석 데이터는 주문별 1행이 아니라 **주문-아이템별 1행**입니다.

| 기준 | 값 |
| --- | ---: |
| 최종 행 수 | 109,294 |
| 고유 `order_id` 수 | 95,784 |
| 고유 `(order_id, order_item_id)` 조합 수 | 109,294 |
| 여러 아이템으로 확장된 주문 수 | 9,507 |

이 기준을 사용한 이유는 상품 카테고리, 상품 무게와 크기, 가격, 배송비, 판매자 정보가 아이템 단위로 제공되기 때문입니다. 리뷰 점수는 주문 단위로 붙습니다. 모델링에서는 `order_id` 그룹 분할로 같은 주문의 아이템이 학습·검증·테스트에 나뉘지 않도록 설계했지만, 성능은 주문·아이템 행 기준으로 계산합니다. 통계검정은 별도로 주문별 1행을 남겨 수행합니다. 그룹 분할과 주문 단위 평가는 서로 다른 절차입니다.

## 5. 주요 결과

### 5.0 결과 집계 단위

리뷰 점수 `review_score`는 `order_id` 기준 주문 단위로 부여됩니다. 반면 최종 모델링 데이터는 상품·셀러·가격·배송비 정보를 보존하기 위해 주문-아이템 단위로 구성했습니다. 리뷰 점수의 평균 차이와 통계검정, 포트폴리오 핵심 차트는 EDA의 학습·검증 영역 87,482행에서 `order_id` 기준 76,627개 주문으로 축약해 계산했습니다. 테스트 주문은 이 통계에 포함하지 않습니다. 같은 리뷰가 여러 아이템 행에 반복 반영되는 것을 피하기 위한 처리입니다.

### 5.1 배송 지연 여부와 리뷰 점수

정상·조기 배송과 지연 배송의 평균 리뷰 점수는 큰 차이를 보였습니다. 리뷰 점수는 주문 단위이므로, `order_id` 기준으로 주문 1건당 1행만 남긴 뒤 비교했습니다.

| 비교 | 평균 리뷰 점수 |
| --- | ---: |
| 정상·조기 배송 | 4.29 |
| 지연 배송 | 2.55 |
| 평균 차이 | 1.74 |

Mann-Whitney U 검정 결과, 배송 지연 여부에 따른 리뷰 점수 차이는 통계적으로 유의했습니다. 이는 배송 지연이 고객 경험 악화와 강하게 연결될 수 있음을 보여줍니다. 다만 관찰 데이터 기반 결과이므로 인과로 단정하지 않습니다.

### 5.2 3일 초과 지연 기준 검정

지연 주문만 대상으로 `0일 초과·3일 이하 지연`과 `3일 초과 지연`을 비교했습니다. 리뷰 점수는 주문 단위인데 분석 데이터는 주문-아이템 단위이므로, 검정 전 `order_id` 기준으로 주문 1건당 1행만 남겼습니다.

| 지연 구간 | 주문 수 | 평균 리뷰 점수 | 중앙값 |
| --- | ---: | ---: | ---: |
| 0일 초과·3일 이하 지연 | 2,086 | 3.75 | 4.0 |
| 3일 초과 지연 | 3,983 | 1.93 | 1.0 |

지연 구간은 실제 도착 시각과 예상 도착 시각의 차이를 일수로 환산한 뒤 소수 첫째 자리로 반올림한 `delay_days` 기준입니다. 모델 입력의 기존 범주 문자열은 보존하고, 표와 차트에서 정확한 구간명을 표시합니다.

검정 결과:

- 관찰된 평균 차이: 1.83점
- Mann-Whitney U 검정: 리뷰 점수 분포 비교, `p < 0.001`
- 순위 기반 효과크기: Rank-biserial correlation `r = 0.594` (짧은 지연 구간의 점수가 높은 방향)

Mann–Whitney U는 평균 차이 1.83점 자체를 검정한 것이 아닙니다. 결과표의 원시 `p_value=0.0`은 수치 계산의 표현 한계이며 실제 확률이 0이라는 의미가 아닙니다. 3일 경계는 데이터 탐색에서 정한 모니터링 후보로, 독립 표본에서 확정한 최적 운영 기준이나 인과 효과로 해석하지 않습니다.

### 5.3 모델 성능

아래 A/B 성능표와 5.3.1 정책 비교표는 수정 전 전처리의 보존 기록입니다. 2026-10-01부터 A/B 평가·학습 노트북에는 학습 전용 결측 대체를 적용합니다. 수정 후 검증 결과와 재현 방법은 아래 12절을 따릅니다.

아래 성능과 Flagged Rate는 모두 주문·아이템 행 기준입니다. 여러 아이템이 있는 주문은 평가에 여러 번 반영되므로 주문별 성능이나 실제 검토 업무량으로 직접 환산할 수 없습니다.

긍정 리뷰 비율이 높은 불균형 데이터이므로, 단순 정확도보다 낮은 만족도 리뷰 재현율, 정밀도, PR-AUC, 균형 정확도, 운영 개입 대상 비율을 함께 봤습니다.

| 모델 | 사용 시점 | 피처 수 | Accuracy | Balanced Accuracy | Risk Precision | Risk Recall | Risk PR-AUC | Flagged Rate | Macro F1 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Track A LightGBM | 배송 완료 후 사후 진단 | 33 | 0.686 | 0.683 | 0.287 | 0.678 | 0.505 | 0.370 | 0.595 |
| Track B LightGBM | 주문 시점 사전 예측 | 22 | 0.624 | 0.622 | 0.235 | 0.619 | 0.289 | 0.413 | 0.539 |

Baseline은 정확도만 보면 높지만 낮은 만족도 리뷰를 하나도 탐지하지 못합니다. 반면 사전 예측 모델은 배송 전 정보만으로도 낮은 만족도 라벨을 가진 평가 행의 약 62%를 탐지해, 선제 안내나 배송 우선순위 판단에 활용할 가능성을 보였습니다. 다만 Track B의 risk precision은 0.235로 높지 않으므로, 이 모델은 자동 의사결정 모델이 아니라 운영자가 먼저 확인할 후보 주문을 좁히는 우선순위 검토 후보 모델로 해석해야 합니다. 보조 용도라는 설명만으로 실무 효용이나 안전성이 검증된 것은 아닙니다.

Track B의 낮은 precision과 PR-AUC, 주문-아이템 단위 평가 문제를 보완하기 위한 면접 후 작업 순서는 [모델링 의사결정 및 수정 기록의 Track B 개선 백로그](docs/modeling_decision_log.md#20-면접-후-track-b-개선-백로그)에 정리했습니다.

### 5.3.1 라벨 정책 민감도 비교

Olist의 `review_score`는 NPS가 아니라 1점부터 5점까지의 별점입니다. 따라서 3점을 부정으로 단정하기보다, 주 모델에서는 3점을 중립으로 제외하고 보조 정책에서 민감도를 비교했습니다.

| 라벨 정책 | 모델링 행 수 | 제외 행 수 | 낮은 만족도 비율 | Track B Balanced Accuracy | Track B Risk Precision | Track B Risk Recall | Track B PR-AUC |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1점·2점 낮은 만족도, 4점·5점 긍정, 3점 제외 | 100,107 | 9,187 | 16.1% | 0.622 | 0.235 | 0.619 | 0.289 |
| 1점·2점 낮은 만족도, 3점부터 5점까지 비위험 | 109,294 | 0 | 14.8% | 0.623 | 0.223 | 0.626 | 0.280 |
| 1점부터 3점까지 CS 리스크, 4점·5점 긍정 | 109,294 | 0 | 23.2% | 0.599 | 0.312 | 0.597 | 0.356 |

첫 번째 기준은 명확한 낮은 만족도를 분석하려는 주 라벨 정책입니다. 3점의 실제 의미가 모두 중립으로 입증됐다는 뜻은 아닙니다. 세 번째 기준의 재현율 0.597은 과거 정책을 포함한 민감도 분석 결과로 보존합니다. 정책마다 평가 대상과 클래스 비율이 달라 단순한 성능 우열이나 주 정책의 통계적 최적성을 주장하지 않습니다.

### 5.4 Track C 예상 배송일 검토값

아래 표는 수정 전 전처리의 보존 기록입니다. 학습 전용 대체 적용 후 결과는 13절의 별도 실험 기록을 따릅니다.

Track B가 낮은 만족도 리뷰 위험 주문을 선별하면, Track C는 해당 주문에 대해 더 보수적인 예상 배송일을 추천합니다. Track C는 주문 시점 정보만 사용해 `delivery_days`의 90% 분위수를 예측하는 LightGBM quantile regression 모델입니다.

90% 분위수는 고정된 정답 임계값이 아니라 검증이 필요한 초기 운영 가정입니다. 실제 운영에서는 지연 감소 효과와 예상 배송일 증가에 따른 구매 전환 손실을 함께 비교해 80%, 90%, 95% 등으로 조정해야 합니다.

| 분위수 기준 | 현재 3일 초과 지연율 | 검토값 적용 시 3일 초과 지연율 | 평균 조정일수 | 조정된 주문·아이템 행 비율 |
| --- | ---: | ---: | ---: | ---: |
| 80% | 5.04% | 4.51% | 0.24일 | 7.78% |
| 90% | 5.04% | 3.50% | 1.22일 | 23.86% |
| 95% | 5.04% | 2.44% | 3.06일 | 43.85% |

이 표는 Track B 고위험 주문으로 필터링하지 않은 **전체 Track C 테스트 행**의 시뮬레이션입니다. 정수형 `delivery_days`와 `expected_delivery_days`의 차이가 3을 초과하는 비율을 계산하므로 EDA의 반올림된 `delay_days`와 정의가 다릅니다. 실제 배송 소요일은 그대로 두고 예상 배송일 검토값만 늘린 결과이며 실제 배송 속도 개선을 뜻하지 않습니다. 평균 조정일수와 `share_orders_adjusted`도 전체 테스트 행 기준입니다. 고위험 주문에만 적용하는 UI 흐름의 효과를 이 표로 주장할 수 없습니다.

| --- | --- | --- | --- | --- |
| 주문 시점 사전 예측 모델 | 주문 확정 직후, 배송 시작 전 | 가격, 배송비, 상품 스펙, 예상 배송일, 지역·거리 정보 | 위험 주문 사전 선별, 출고 상태 우선 확인, 선제 안내 대상 선정 | 고객 불만이 발생하기 전에 개입할 수 있음 |
| 배송 완료 후 진단 모델 | 배송 완료 후, 리뷰 작성 전후 | 실제 배송일, 지연일, 배송 속도 등 배송 결과 정보 | 불만 원인 진단, CS 우선순위 판단, 보상·환불 검토, 판매자 운영 점검 | 이미 발생했거나 발생 가능성이 높은 불만을 원인 중심으로 대응할 수 있음 |
| 예상 배송일 추천 모델 | Track B 고위험 주문 선별 후 | 주문 시점 정보, 현재 예상 배송일 | 고위험 주문의 보수적 예상 배송일 추천, 고객 안내 기준 보정 | 예상 배송일 변경을 검토하는 운영 가설이며 실제 효과는 미검증 |

두 모델은 우열 관계가 아니라 사용 시점이 다릅니다. 사전 예측 모델은 배송 전에 개입하기 위한 모델이고, 배송 완료 후 진단 모델은 실제 배송 결과까지 반영해 CS 대응과 운영 개선의 근거를 만드는 모델입니다.

### 6.2 3일 초과 지연 주문은 별도 리스크 구간으로 관리

0일 초과·3일 이하 지연과 3일 초과 지연의 평균 리뷰 점수 차이는 1.83점이었고, 효과크기도 큰 수준이었습니다. 따라서 3일 초과 지연 주문은 일반 지연 주문과 구분해 우선 모니터링 대상으로 둘 수 있습니다.

운영 제안:

- 예상 배송일을 3일 넘겨 초과할 가능성이 있는 주문을 조기 탐지
- 고객에게 지연 상황과 예상 도착일을 선제 안내
- 반복적으로 3일 초과 지연이 발생하는 판매자·지역·상품군을 별도 점검

### 6.3 주문 시점 사전 예측 모델로 위험 주문을 먼저 선별

배송 완료 후 정보만으로 원인을 분석하면 고객 불만이 이미 발생한 뒤입니다. 주문 시점 사전 예측 모델은 가격, 배송비, 상품 스펙, 예상 배송일, 지역·거리 정보만 사용하므로 배송 전에 개입할 수 있습니다.

운영 제안:

- 사전 예측 모델로 고위험 주문을 우선 모니터링
- 고위험 주문은 출고 지연 여부를 더 빠르게 확인
- 배송 우선순위 조정이나 선제 안내 대상으로 활용

### 6.4 배송 완료 후 진단 모델로 CS 대응 우선순위 판단

배송 완료 후에는 실제 배송일, 지연일, 배송 속도 같은 사후 정보를 사용할 수 있습니다. 이 정보는 이미 발생한 불만의 원인을 진단하고, CS 보상이나 판매자 운영 점검의 우선순위를 정하는 데 적합합니다.

운영 제안:

- 리뷰 작성 전후의 고위험 주문을 CS 우선 확인 대상으로 분리
- 3일 초과 지연, 장거리 배송, 출고 지연 주문을 함께 점검
- 보상·환불·판매자 피드백 기준을 데이터 기반으로 정교화

주의할 점은 이 제안들이 관찰 데이터 기반 분석에서 나온 운영 가설이라는 것입니다. 실제 정책으로 적용하려면 A/B 테스트나 파일럿 운영을 통해 고객 만족도, 비용, 재구매율 변화를 추가로 검증해야 합니다.

### 6.5 Track B와 Track C를 연결한 운영 콘솔

Streamlit UI를 통해 운영자가 주문 정보를 입력하면 Track B가 낮은 만족도 리뷰 위험도를 예측하고, 고위험 주문에 대해 Track C가 추천 예상 배송일을 제안합니다.

운영 흐름:

```text
테스트 주문 예시 선택 또는 주문 정보 입력
→ Track B 낮은 만족도 리뷰 위험도 예측
→ 고위험 주문 판정
→ Track C 선택 분위수 배송 소요일 예측
→ 추천 예상 배송일과 운영 액션 제시
```

UI의 `테스트 주문 예시`는 전체 데이터에서 임의로 뽑은 샘플이 아니라, `order_id` 기준 holdout split 이후 학습에 사용하지 않은 주문입니다. Track B 판정은 낮은 만족도 리뷰 위험 확률 기준으로 나누며, Track C 추천 예상 배송일은 고위험 주문에만 운영 액션으로 적용합니다.

Track B 고위험 기준과 Track C 분위수 기준은 운영자가 직접 조정할 수 있습니다. 기본값은 검증셋에서 선택한 Track B 기준과 90% 분위수 운영 가정에 기반합니다.

| Track B 판정 | 낮은 만족도 리뷰 위험 확률 | Track C 적용 | 운영 의미 |
| --- | ---: | --- | --- |
| 고위험 | 46% 초과 | 적용 | 판매자가 별도 확인해야 할 주문 |
| 주의 | 35% 초과부터 46% 이하 | 미적용 | 배송 상태 모니터링 대상 |
| 일반 | 35% 이하 | 미적용 | 일반 처리 |

조정 가능한 운영 기준:

- Track B 고위험 기준: 기본 46%
- Track B 주의 기준: 기본 35%
- Track C 분위수 기준: 기본 90%, 선택 후보 80%, 85%, 90%, 95%

## 7. 모델 설계 판단

### Track A: 배송 완료 후 사후 진단 모델

배송 완료 후에만 알 수 있는 실제 배송일, 지연일, 배송 속도 등을 포함합니다. 이 모델은 주문 시점 예측용이 아니라, 리뷰 결과가 나온 뒤 CS·운영팀이 어떤 배송 요인이 불만과 연결됐는지 진단하는 용도입니다.

### Track B: 주문 시점 사전 예측 모델

배송 완료 후 정보는 제외하고, 주문 시점에 이미 알 수 있는 가격, 배송비, 상품 스펙, 예상 배송일, 지역·거리 정보만 사용합니다. 이 모델은 리뷰가 작성되기 전에 위험 주문을 선별하는 목적입니다.

이렇게 두 모델을 분리한 이유는 모델이 실제 운영 시점에 알 수 없는 미래 정보를 사용하면 평가 성능이 과대평가될 수 있기 때문입니다.

## 12. A/B 학습 전용 결측 대체 반영 — 2026-10-01

`src/olist_imputation.py`의 `TrainOnlyImputer`를 A/B 학습 파이프라인에 넣었습니다. 도시별 좌표 최빈값·상품 중앙값·거리 중앙값은 `fit`에 전달된 학습 행에서만 계산하고 검증·테스트에는 적용만 합니다. 교차검증에서도 fold별로 통계를 다시 계산합니다. 미등록 도시의 좌표는 결측으로 두고 남은 거리를 학습 거리 중앙값으로 대체합니다.

- 입력: 기존 `data/processed/ml_data.csv`와 대체 전 원본 `data/processed/merged_data.csv`. 두 파일을 주문·아이템 복합키로 일대일 연결합니다. 원본 보조 열은 대체 후 제거되어 A 33개·B 22개 피처를 유지합니다.
- 진입점: `prepare_corrected_model_frame` → `build_corrected_track_pipeline` → 학습. `evaluate_track_a_vs_b`, `evaluate_track_b`, `evaluate_label_policies`도 이 경로를 사용합니다. 외부 입력은 `raw_data`로 대응 원본을 제공할 수 있습니다.
- 노트북: `03_ml_classifier.ipynb`도 같은 전처리를 사용합니다. 기존 `ml_data.csv`를 덮어쓰지 않으며 비교표는 `outputs/experiments/ab-notebook-실행시각/`에 저장합니다. 수정 전 학습 출력은 커밋 `a1145c7`에 보존하고 현재 노트북에서는 제거했습니다. 전체 노트북·하이퍼파라미터 탐색은 재실행하지 않았습니다.
- 생성 스크립트의 출력은 `outputs/experiments/generated-tracks-실행시각/`로 분리했습니다. 이 스크립트는 이번 검증에서 실행하지 않았습니다.
- 당시 별도로 남겨둔 UI·Track C 경로도 아래 13절에서 이관했습니다. A/B 평가와 UI는 학습 표본이 다르므로 결과를 구분합니다. EDA 스냅샷·과거 성능표·포트폴리오는 그대로 보존합니다.

실제 A/B 학습의 검증·테스트 확률은 앞선 학습 전용 대체 실험과 최대 차이 0이었습니다. 동일 분할에서의 구현 재현 검증이며 새 일반화 성능 인증은 아닙니다.

## 13. UI·Track C 학습 전용 대체 반영 — 2026-10-02 기록

UI는 `streamlit_app.py`의 주문·상품 정보 입력 및 결과 표시 화면입니다. 2026-10-01에 UI B/C, Track C 평가, 추천 예시와 전체 학습 진입점까지 학습 전용 대체를 연결했습니다. `train_models`는 입력 전체를 학습하는 함수이므로 holdout 평가 함수와 구분합니다. 기존 저수준 빌더는 과거 실험 재현용으로 남깁니다.
